How Letterbot works

From an email arriving in your inbox to a Telegram message landing on your phone — every step explained.

The email pipeline

6 stages, each with a clear purpose.

Stage 1: IMAP polling — how does Letterbot read new email? −
Letterbot connects to your IMAP server in read-only mode using standard IMAP IDLE or periodic polling (configurable). It fetches new UID ranges since the last sync, respecting UIDVALIDITY to detect mailbox resets. It never modifies, deletes, or flags any email. The raw email is parsed locally — headers, text body, and attachment list are extracted in-memory.
Stage 2: Extraction — what does Letterbot extract from an email? +
Body segmentation removes forwarded headers, disclaimers, quoted text, and signatures to isolate the original message. Attachment text is extracted from PDF and .xlsx files using open-source libraries. Named entities (person names, companies, monetary amounts, dates) are resolved with confidence scores. Email type is classified (INVOICE, CONTRACT, SECURITY_ALERT, NEWSLETTER, etc.).
Stage 3: AI analysis — when and how is an external LLM used? +
If an LLM provider is configured, the cleaned email body (not attachments, not raw headers) is sent for classification and summary generation. This step is optional — Letterbot runs fully in deterministic mode without LLM. If the LLM fails or is unavailable, the system automatically falls back to deterministic analysis and enters DEGRADED_NO_LLM mode.
Stage 4: Priority decision — how is the final priority determined? +
Priority is computed by the priority engine combining multiple signals: LLM classification (if available), email type, sender history (relationship score, frequency baseline, anomaly detection), keyword patterns, attachment type, and any prior user corrections from the same sender. The result — 🔴 Urgent / 🟡 Important / 🔵 Low — is accompanied by a reason code string that explains the dominant factor.
Stage 5: Telegram delivery — what is sent and how? +
A formatted Telegram message is constructed: priority emoji + type label, sender display name, subject, 2–3 line summary, suggested action, attachment note if applicable, and inline buttons for priority adjustment and snooze. The message is sent via the Telegram Bot API with retry-on-failure and exponential backoff. Delivery outcome and latency are logged for the observability cockpit.
Stage 6: Learning — how does Letterbot adapt over time? +
When you tap a priority button in Telegram, the callback is received by Letterbot's inbound handler. The correction is persisted to the local database as a training signal. Sender relationship profiles and frequency baselines are updated. Over successive corrections, the priority engine's sender-level weights shift toward your actual attention patterns.

What does the architecture look like?

# Letterbot data flow (simplified) IMAP server → letterbot IMAP poller → extractor ↓ priority engine (deterministic + optional LLM) ↓ Telegram ← delivery formatter ← validator ↓ user tap → inbound handler → SQLite (local) → learning signal # Local observability (no internet) localhost:8787 ← web cockpit ← SQLite read-only
🗄

Storage: local SQLite

All state lives in a single SQLite file on your machine. Email metadata, priority history, snooze queue, correction signals, sender profiles, SLA metrics, events. No network database, no cloud sync. Portable — copy the file to move your history.

🔒

Single-flight LLM design

Letterbot uses a global LLM lock (single-flight pattern) — one request at a time. This prevents API rate limit violations on free tier LLM APIs (GigaChat, Cloudflare Workers AI) and ensures predictable resource usage on low-RAM hardware.
